  manifest->env-config round-trip in `tests/test_rl_visualizer.py` (SB3-free).

### B9 - Sub-Tick Finish-Line Lap Timing

Status: Done (2026-06-21). Implemented in the reporting/metrics layer only; physics,
collision, finish detection, RL reward, and termination are untouched. `Gate` now
exposes `crossing_with_fraction()` (the `crossing() -> int` contract is unchanged);
`RunState` stores `finish_fraction` and `lap_time()` returns the sub-tick crossing
time `(lap_ticks - (1 - finish_fraction)) * dt`, while `lap_ticks` stays the canonical
integer the state machine, replay validation, and reward read. `TIMING_VERSION`
("timing_v2") is stamped into completed-run metrics and RL rollout summaries so old
integer-tick records stay distinguishable; legacy records read back as "timing_v1".
`PHYSICS_VERSION` unchanged. Tests + `python -m momentum_lab.eval` green.

Migration done (2026-06-21): `momentum_lab/rl/retime.py` (`python -m momentum_lab.rl.retime`)
re-times every saved run from its cached frames -- the finish-crossing fraction
recovered from the two frames straddling the close is bit-identical to a live
re-run, so no re-running/re-training is needed and it is physics-version
independent. Rewrote 89 rollout artifacts, 89 summary rows, and both `replays/`
files to sub-tick + `timing_v2` (idempotent; 3 stale top-level `eval_summaries.jsonl`
rows whose artifacts were relocated have no frames to re-time and are left as
`timing_v1`). Added `timing_version` to `ReplayData` so future in-game bests/ghosts
are self-describing. Leaderboard (`ranked_runs.md`), analytics `index.html`, the
replay viewer, and per-run SVGs now render millisecond precision (`.2f` -> `.3f`)
and were regenerated. Outcome: the b8 best (4.020 s) and the human `750982`
(4.028 s) -- previously both 4.033 s / 242 ticks -- are now distinguished, and the
policy edges the human on reported sub-tick time.

Original ticket (context). Raised by the user after noticing lap times quantize to
1/60 s (16.67 ms) steps, so distinct runs land on identical displayed times.

Why: Lap time is tick-derived (`RunState.lap_ticks = finish_tick - start_tick`,
integer control ticks at `CONTROL_HZ = 60`), so every lap time is a multiple of
`CONTROL_DT = 1/60 s`. Real racing games report ~0.001 s by interpolating the
finish-line crossing within the step. The coarse staircase hurts time-trial feel and
collapses RL lap-time discrimination (many distinct policies tie on the same tick
count -- e.g. the b7 246-tick pile-up and the b8 256/258/259 clustering).

Key enabling fact: `Gate.crossing()` (`core/checkpoints.py`) **already computes the
crossing fraction** `t = s0 / (s0 - s1)` along the prev->cur move segment, then
discards it and returns only the integer direction. The sub-tick fraction is already
in hand; it just is not surfaced.

Scope (reporting/metrics layer ONLY -- must not touch physics or the RL env):

- Expose `t` from the finish crossing (and optionally each checkpoint split) without
  changing the existing `crossing() -> int` contract used by the state machine.
- In `RunState`, store a fractional finish offset: true crossing time is
  `lap_ticks - (1 - t)` ticks. Add a `lap_seconds` that applies it; keep the integer
  `lap_ticks` as canonical for the tick-driven state machine and replay validation.
- Keep the timer START at the first-throttle tick (a discrete input event, not a
  geometric crossing -- interpolation is neither needed nor meaningful there).
- Surface the fractional time in HUD / best-lap / live delta and in metrics/analytics.

Break analysis (answers "does it break the game/models?"):

- Game: no. Physics, collision, checkpoint advance, and finish detection (the
  `crossing() > 0` boolean) are unchanged; the lap still closes on the same tick. Only
  the reported time gains a fractional part (slightly smaller -- no longer rounded up
  to the full tick).
- Models: no, and no retraining. Episodes still terminate on the integer finish tick;
  the per-step reward and the observation never see `lap_time`. Confine the sub-tick
  value to the reporting/metrics path (never the env reward/termination) and training
  is identical; saved models load and drive bit-identically. `keep-best` selection by
  `lap_time` merely gains finer discrimination.
- Determinism: preserved. `t` is a pure function of two deterministic positions plus
  gate geometry -- no wall-clock, no RNG. `PHYSICS_VERSION` / physics fingerprint need
  NOT change (physics untouched). Bump a separate timing/metrics version marker so old
  integer-tick `lap_time`s stay distinguishable from new sub-tick ones.

Data availability: fully present. Live, `Gate.crossing` has `t`. Retroactively, the
replay frame caches store per-control-tick `x,y`, so every saved run (human `750982`
and all RL rollouts) can be re-timed from the two frames straddling the finish gate --
no re-running. Interpolation is linear between 60 Hz samples; that is the standard
precision and is independent of the 120 Hz physics substeps.

Migration:

- Re-time the human reference and saved bests for apples-to-apples comparison, or keep
  both and label old records as tick-rounded. Old vs new times stay monotonic, so
  mixed comparison is safe but cosmetically off by < 1/60 s.
- Update any test asserting exact integer-tick `lap_time` values.

Acceptance:

- Lap times report sub-tick (~ms) precision; two runs finishing on the same control
  tick but crossing at different points within it show different times.
- `python -m pytest -q` and `python -m momentum_lab.eval` stay green (determinism and
  replay validation unaffected).
- No change to RL training dynamics or saved-model behavior; the sub-tick value never
  enters the env reward/termination.
