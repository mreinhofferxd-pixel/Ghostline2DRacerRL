# Ghostline Portfolio Challenge Implementation Plan

## Goal

Add Ghostline to the portfolio as an interactive case-study section.

The portfolio should do more than link to GitHub. The GitHub repo is source/proof,
while the website should let visitors understand the story, watch the replay
viewer, and try the challenge themselves.

Core experience:

- Tell the RL story: deterministic racer, reward design, replay proof, final AI lap.
- Embed or link the existing replay/story viewer.
- Add a small browser-playable "Try to beat Ghostline" challenge.
- Show fixed benchmark rows:
  - Ghostline AI: 3.965s, 239 ticks, 0 walls.
  - Michi/dev: 4.028s, 242 ticks, 0 walls.
- Later add a verified public leaderboard for visitor attempts.

## Phase 2: Browser-Playable Local Challenge

Goal: build a playable "try to beat Ghostline" challenge with local-only scoring.

Build a small TypeScript/Canvas version of Ghostline.

Suggested portfolio repo structure:

```text
src/features/ghostline/
  sim/
    action.ts
    car.ts
    config.ts
    collision.ts
    checkpoints.ts
    timing.ts
    track.ts
    physics.ts
    simulation.ts
  game/
    GhostlineChallenge.tsx
    input.ts
    renderer.ts
    recorder.ts
    ghosts.ts
    localLeaderboard.ts
```

Port only what the browser challenge needs:

- `Action`
- car state
- fixed-step simulation
- physics integration
- swept circle-vs-segment collision
- boost pads
- checkpoints
- finish timing with sub-tick reporting
- wall hit counting
- action stream recording

Browser controls:

- Arrow up / W: throttle
- Arrow down / S: brake/reverse
- Arrow left / A: steer left
- Arrow right / D: steer right
- Space / Shift: drift
- R: restart

Rendering:

- Canvas draws track surface, inner/outer boundaries, checkpoints, finish, and
  boost pads.
- Draw player car.
- Draw AI ghost and dev ghost from exported frame/action data.
- Keep UI compact and portfolio-friendly.

Local scoring:

- Save best valid run to `localStorage`.
- Store:
  - lap time
  - lap ticks
  - wall hits
  - action stream
  - date
  - physics version
- Do not implement public submission yet unless Phase 2 feels good.

Acceptance:

- User can complete a lap in the browser.
- Valid lap detection works.
- Timer starts only on first throttle.
- Ordered checkpoints are enforced.
- Local best persists after reload.
- AI/dev ghost overlays render correctly.
- Mobile layout is clean, even if keyboard gameplay is desktop-first.

## Phase 3: Golden Tests For Browser Sim

Goal: make sure the browser sim stays close to the canonical Python sim before
any public leaderboard trusts it.

Add fixture generation in `2DRacerRL`.

Generate fixtures from Python:

```text
public/ghostline/fixtures/
  straight_accel.json
  brake_turn.json
  wall_collision.json
  boost_pad.json

Each fixture should contain:

  "name": "ai_record_replay",

  "track_id": "track_01_easy_loop",

  "expected": {
    "lap_time": 3.965,
    "lap_ticks": 239,
    "wall_hits": 0,
    "final_state_hash": "..."
  }
}
```

In the portfolio repo:

- Add Vitest/Jest tests that run the TypeScript sim against fixtures.
- Allow tiny float tolerance for positions/speeds.
- Require exact checkpoint/lap/wall outcomes.

Acceptance:

- Browser sim matches canonical Python outcomes closely enough.
- AI record replay validates as `3.965s / 239 ticks / 0 walls`.

## Phase 4: Verified Public Leaderboard

Goal: public attempts, but believable.

Important rule:

The browser must never submit "I got 3.8s, trust me." It submits the action
stream. The server recomputes the run.

Submission payload:

```json
{
  "driver": "ABC",
  "track_id": "track_01_easy_loop",
  "physics_version": "physics_v4",
  "actions": [[1, 0, -1, false], [1, 0, -1, false]]
}
```

Server verification:

- Load canonical track.
- Re-run the action stream through the authoritative sim.
- Validate:
  - correct physics version
  - valid lap
  - all checkpoints in order
  - finish crossed correctly
  - reasonable max action length
- Compute:
  - lap time
  - lap ticks
  - wall hits
  - action stream hash
  - replay hash
- Store only verified results.

Leaderboard rows should separate fixed benchmarks from visitor attempts:

```text
Benchmarks
1. Ghostline AI  3.965s  0 walls
2. Michi/dev     4.028s  0 walls

Visitor Attempts
1. ABC           4.912s  1 wall
2. XYZ           5.203s  0 walls
```

Backend options:

- Vercel/Next API route plus Postgres.
- Supabase function plus table.
- Cloudflare Worker plus D1.
- Any simple API/database stack already used by the portfolio.

Example database table:

```sql
ghostline_runs (
  id uuid primary key,
  driver text not null,
  track_id text not null,
  physics_version text not null,
  lap_time numeric not null,
  lap_ticks integer not null,
  wall_hits integer not null,
  valid boolean not null,
  actions_json jsonb not null,
  replay_hash text not null unique,
  created_at timestamptz not null default now()
)
```

Add basic abuse protection:

- Initials/name length limit.
- Action stream max length.
- Rate limiting by IP/session.
- Profanity filter or manual moderation if names are public.
- Dedupe identical replay hash.

1. Portfolio case-study page with exported static replay viewer.

## Do Not Do

- Do not make GitHub the main experience.
- Do not trust client-submitted lap times.
- Do not change Python physics just to make the browser port easier.
- Do not manually copy `file://` paths into production.
- Do not mix visitor leaderboard rows with the fixed AI/dev benchmarks as if they
  were the same category.
